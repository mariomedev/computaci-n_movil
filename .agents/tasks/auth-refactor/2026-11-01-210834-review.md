# Atomic Design refactoring for authentication screens

Auth screens refactored using Atomic Design pattern, extracting reusable components into atoms (AuthTextField, PasswordVisibilityButton, ThemeToggleButton), molecules (AuthFormField with integrated validation, AuthLogoHeader, ErrorMessageBanner), and organisms (LoginForm, RegisterForm). Screens now delegate layout and business logic to organisms, reducing from ~200 lines to ~100 lines each. All validations, styling, and Riverpod integration preserved.

**Watch for:** Validation logic duplicated in molecule and domain layer **(confirmed)**. Password visibility state living in molecule breaks single responsibility **(confirmed)**. Missing phone number formatting sanitization in screen **(confirmed)**.

**Verdict**: CHANGES_REQUESTED

## High-level view

Validation rules are implemented twice: AuthFormField's `_validate` method duplicates the same email format and password length checks that already exist in domain use cases (SignInUseCase, SignUpUseCase). This creates a maintenance burden where changing validation rules requires updating two locations, and the domain layer's validation becomes unreachable dead code since the form prevents submission.

AuthFormField manages password visibility state (`_obscureText`) internally as a StatefulWidget. This mixes presentation concerns (toggling visibility icon) with form field composition. The same pattern appears in both LoginForm and RegisterForm contexts, but each instantiation carries its own independent state management rather than treating visibility as a pure display concern controlled by the parent.

RegisterScreen sanitizes phone input before passing it to the use case (`text.trim().replaceAll(RegExp(r'[^\d+]'), '')`), but this preprocessing logic lives in the screen's `_submit` method rather than in the RegisterForm organism or the domain layer. If phone validation changes or another screen needs phone input, the sanitization won't be reused.

## Validation lives in two places

AuthFormField's `_validate` method implements email format checking (`RegExp(r'^[^@]+@[^@]+\.[^@]+$')`), password length requirements (6 characters minimum when `requirePasswordLength` is true), and phone format validation (`RegExp(r'^[0-9+\s()-]{7,20}$')`). These same rules exist in domain use cases: SignInUseCase checks email format before calling repository, SignUpUseCase validates password length of 6+ characters, and similar patterns appear throughout the domain layer.

The form-level validation runs first, preventing submission if any field is invalid. This means domain-layer validation never executes in the success path—it only runs if someone bypasses the UI or calls the use case directly from tests. Changing a validation rule requires updating both the molecule's `_validate` switch statement and the corresponding use case, with no compile-time enforcement that both stay in sync.

```dart
// In auth_form_field.dart
if (widget.requirePasswordLength && value.length < 6) {
  return 'Contraseña debe tener al menos 6 caracteres';
}

// In sign_up_use_case.dart (unreachable via UI)
if (authParams.password.length < 6) {
  return const Left(
    ValidationFailure(message: 'Contraseña debe tener al menos 6 caracteres'),
  );
}
```

The domain layer should be the single source of truth for business rules. Form validators should either delegate to domain logic or perform only format/non-empty checks that prevent unnecessary network calls, not reimplement business validation.

## Password obscuring state embedded in molecule

AuthFormField is a StatefulWidget with `_obscureText` boolean state. When `type` is password or confirmPassword, the molecule renders PasswordVisibilityButton (an atom) and passes it `onPressed: () { setState(() { _obscureText = !_obscureText; }); }`. The obscured state is scoped to each field instance.

This makes AuthFormField responsible for both composition (which atoms to combine) and behavior (managing visibility toggle state). LoginForm creates two AuthFormField instances (email, password), each carrying its own state. RegisterForm creates eight fields, three with independent password visibility state.

PasswordVisibilityButton is stateless—it receives `isObscured` and `onPressed` as props. The visibility state could live in the organism (LoginForm/RegisterForm) or even higher in the screen, treating obscuring as a display concern rather than a molecule-level behavior. Currently there's no reuse benefit to having the state in the molecule; each field has isolated state anyway.

## Phone number formatting split between layers

RegisterScreen's `_submit` method reads `_telefonoController.text.trim()` and then calls `.replaceAll(RegExp(r'[^\d+]'), '')` to strip non-digit characters before passing to the use case. This sanitization happens in the screen layer, after the molecule has validated format (`r'^[0-9+\s()-]{7,20}$'`), which allows spaces, parentheses, and hyphens.

The molecule allows formatted input (e.g., "(555) 123-4567"), the screen strips formatting before submission, and the domain layer receives clean digits. If another screen collects phone input, it will need to replicate this stripping logic. The validation regex and sanitization pattern are coupled but live in different layers.

AuthFormField with `type: AuthFormFieldType.phone` could apply sanitization directly in its controller, or RegisterProfileParams could enforce the format in a factory constructor, or SignUpUseCase could normalize the input. Currently, the rule is implicit in the screen's submit handler.

## Components lack documentation

Components have no dartdoc comments. AuthFormField has 8 constructor parameters (`labelText`, `prefixIcon`, `type`, `controller`, `enabled`, `passwordController`, `fieldName`, `requirePasswordLength`) with no explanatory comments about when to use `passwordController` (only for confirmPassword type) or what `requirePasswordLength` gates (6-char minimum vs no length check). Organisms would benefit from summary comments explaining their role in the Atomic Design hierarchy and when to use them versus composing molecules directly.

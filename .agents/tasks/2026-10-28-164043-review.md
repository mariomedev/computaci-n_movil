# Register screen implementation

The RegisterScreen adds a complete registration flow to the Lapticon Flutter app, mirroring the LoginScreen's design patterns while handling seven form fields (email, password, confirm password, nombre, apellido, telefono, nacionalidad). The screen validates all inputs, manages password visibility toggles for both password fields, and calls `authStateProvider.signUp()` with the required parameters. Navigation flows through the existing router with proper unauthenticated access to `/register`.

**Watch for:** Missing listenManual pattern for auth state redirect (likely) — the navigation to dashboard on successful registration uses `ref.listen` in the build method instead of `ref.listenManual` in `initState` like LoginScreen. Telefono validation allows spaces and parentheses but strips them before submission, creating a display vs. submission mismatch (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The redirect on successful registration uses `ref.listen` directly in the build method, where LoginScreen uses `ref.listenManual` wrapped in `addPostFrameCallback` inside `initState`. This pattern difference could cause the registration redirect to fire on every rebuild instead of only when the auth state transitions to `AuthAuthenticated`.

The telefono validator accepts formatting characters (`+`, spaces, `()`, `-`) but the submit handler strips everything except digits and `+` before passing to `signUp()`. This means a user can enter "(555) 123-4567" which validates successfully, but the backend receives "5551234567", breaking the validation contract.

## Auth redirect pattern mismatch

RegisterScreen sets up the auth state listener inside the build method:

```dart
@override
Widget build(BuildContext context) {
  // Escuchar cambios en el estado de autenticación
  ref.listen<AuthState>(authStateProvider, (previous, next) {
    if (next is AuthAuthenticated) {
      // Navegar al dashboard cuando se registre
      context.go(AppRoutes.dashboard);
    }
  });
```

LoginScreen uses a different pattern, setting up the listener in `initState`:

```dart
@override
void initState() {
  super.initState();
  // Escuchar cambios en el estado de autenticación
  WidgetsBinding.instance.addPostFrameCallback((_) {
    ref.listenManual(authStateProvider, (previous, next) {
      if (next is AuthAuthenticated) {
        // Navegar al dashboard cuando se autentique
        context.go(AppRoutes.dashboard);
      }
    });
  });
}
```

The difference matters. `ref.listen` in the build method executes on every rebuild, potentially creating multiple listeners or evaluating the redirect logic repeatedly. `ref.listenManual` wrapped in `addPostFrameCallback` inside `initState` runs once after the first frame, establishing a single persistent listener. The LoginScreen pattern is the correct approach for side effects like navigation.

RegisterScreen should adopt the same pattern: move the listener setup to `initState`, wrap it in `addPostFrameCallback`, and use `listenManual` instead of `listen`.

## Telefono validation and submission mismatch

The telefono validator accepts digits, `+`, spaces, parentheses, and hyphens:

```dart
String? _validateTelefono(String? value) {
  if (value == null || value.trim().isEmpty) {
    return 'Teléfono es requerido';
  }
  final regex = RegExp(r'^[0-9+\s()-]{7,20}$');
  if (!regex.hasMatch(value.trim())) {
    return 'Teléfono debe tener formato válido';
  }
  return null;
}
```

The submit handler strips all formatting characters except digits and `+`:

```dart
final telefono = _telefonoController.text.trim().replaceAll(
  RegExp(r'[^\d+]'),
  '',
);
```

This creates a validation contract that the backend never sees. A user enters "(555) 123-4567", the validator accepts it, but the backend receives "5551234567". If the backend expects formatted input or validates against a different pattern, this will fail silently or cause unexpected behavior.

The fix depends on backend expectations. If the backend wants formatted strings, remove the `replaceAll` in submit. If it wants raw digits, tighten the validator to reject formatting characters and guide users toward unformatted entry.
